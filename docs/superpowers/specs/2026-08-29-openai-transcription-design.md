# OpenAI 音声認識と区間単位の安全な再開

作成: 2026-08-29。対象: 0.5.0。実装・ソース検証済み。公開は未了。

## 公開範囲

既存のローカル Whisper を維持し、OpenAI 接続から `whisper-1` と
`gpt-4o-transcribe-diarize` を選べるようにする。音声認識の設定・送信確認・
失敗後の再開はアプリ、公開 MCP、製品 CLI で同じ経路を使う。
契約は 5.0.0。新しい公開ツールは追加せず、既存 37 ツールを拡張する。
画像入力、音声の任意切り出し、既知話者の参照音声、成功区間の強制再送は対象外。
全工程の `ProcessingConfig` 移行、Claude Agent SDK による生成、複数案の生成・統合も別の範囲とする。
同梱アプリは契約 5.0.0 と厳密に照合し、製品 CLI は契約メジャー版 5 を要求する。
開発用 Swift の旧契約 2 / 3 / 4 への接続では各版の対応範囲だけを扱い、音声認識対応を推測しない。

## 設定と操作

アプリの手順は OpenAI 接続の準備 → 音声認識モデル・言語・送信許可の保存 → 再生成の確認、とする。

1. 「AI 接続」で OpenAI API のキーを保存し、「確認・準備」と「モデル一覧で接続を確認」を完了する。Codex の認証情報は使わない。
2. 会議の「設定」または「プロファイル」で、「文字起こしの処理方法」を「OpenAI API を使う」にする。
3. 「音声認識用の OpenAI 接続」→「音声認識モデル」を選ぶ。「音声認識の候補を取得・更新」で明示的に照会し、画面表示時は保存済み候補だけを読む。
4. 共通の「言語（auto / ja / en など）」と `api_ok` を確認して保存する。保存だけでは音声を送らない。
5. 議事録タブの「再生成」で、音声認識と後段の議事録生成の内容を確認して開始する。

- 会議・プロファイルに nullable な `transcription_model` を追加する。
- 選択は `provider=openai-api`、接続 ID・revision、上記のモデル ID、
  閉じた `parameters={}`、非負整数の `cache_epoch` を持つ。
- 未指定は既存状態を保持し、null でローカル設定へ戻す。
  `transcription_engine` はローカル設定として保持し、API 選択時だけ使用しない。
- `set_meeting_config` / `set_profile` は任意の `expected_config` を受け付け、
  指定された場合は保存前の全設定一致を検査する。アプリの API 音声設定と
  再送用 epoch の保存はこれを使い、別操作の変更を上書きしない。
  新しいプロファイルの比較基準は既定の `MeetingConfig` とする。
  プロファイルの置換開始後に保存エラーが起きた場合は、適用済みの可能性を示し、
  再読み込みするまで保存成功や未適用と決めつけない。
- `language` は既存の共通設定を使う。API では実在する小文字2文字の ISO 639-1 コード、
  または `auto` を許可する。UI の空欄は保存済み値を維持し、未設定なら `ja` とする。
  `auto` のときは API の language を省略する。
- 初期版の API 経路は用語ヒントを送らない。登録語彙は発話統合で引き続き使い、
  その区別を設定画面に表示する。非対応の prompt・話者参照等は送信前に拒否する。
- API の選択には `api_ok` の明示設定が必要。接続・モデル・言語と、
  マイクとシステム音声を別々に送ること、追加課金の可能性を表示する。
  保存・候補表示だけでは音声を送らない。
- 対応経路は `capabilities.transcription_model_providers` で通知する。
  常駐サーバーでは OpenAI、非常駐では空配列とし、認証状態とは区別する。
- OpenAI 接続を共用し、モデル候補と UI キャッシュは llm / transcription の用途で分ける。
  時刻付き結果を扱えない音声モデルを推測で選択可能にしない。

「ローカルの設定を使う」で保存すると API の選択を解除する。ローカルエンジン・
既存の話者分離・マイク本人判定・議事録モデルは別設定として維持する。
OpenAI の接続確認はモデル一覧取得の確認に限り、残高・認識権限・実認識品質の確認とは扱わない。

## 音声と送信

既存の前処理による 16 kHz・mono・PCM16 WAV を使う。通常区間は
9,600,000 samples（10分）、末尾だけ短くする。非重複・無欠落で固定順に分割し、
mic → system の順で会議全体を逐次処理する。各ファイルはヘッダー込みで
24,000,000 bytes 以下、全体は最大 144 区間・合計24時間の音声に制限する。
これはアプリの送信上限であり、料金の上限や API 側の処理回数を保証しない。
入力 WAV の sample 以外のメタデータは合計1 MiB以下に制限し、分割した送信用
WAV には含めない。これは入力の走査を制限するアプリ側の上限である。

送信は `POST https://api.openai.com/v1/audio/transcriptions` に限定する。
接続に保存したキーだけを使い、環境変数・別接続・別モデルへ切り替えない。
multipart の filename は `audio.wav` とし、会議名・絶対パスを送らない。
語彙ヒント・話者名指定・参照音声も追加送信しないが、音声自体に発言中の名前などが含まれ得る。

| モデル | 固定要求 |
|---|---|
| whisper-1 | verbose_json、segment / word の timestamp_granularities |
| gpt-4o-transcribe-diarize | diarized_json、chunking_strategy=auto、stream=false |

Responses の tools / store / reasoning / max_output_tokens は転用しない。
HTTP の proxy・redirect・自動再送を禁止し、送受信の容量・絶対期限・取消を共用する。
各送信直前に、設定・api_ok・接続版・キー・実行環境・モデル能力・終了日を再検査する。

## 応答と話者

native の segment / word 時刻に区間の開始 sample / 16000 を一度だけ足す。
有限値、非負、区間の逆転、音声範囲を検査し、時刻の補完や黙った切り詰めはしない。
異なる話者の重なりは禁止しない。時刻付き区間のない非空テキストは成功にしない。
無音の空テキスト・空区間は成功として扱える。

Whisper の単語時刻は native の情報だけを保存する。Diarize の話者ラベルは
track / chunk の名前空間に閉じ、実名や区間をまたぐ同一人物と解釈しない。
既存の話者分離を明示選択している場合はその設定を維持する。
ASR 由来の匿名話者は独立した根拠として統合へ渡し、マイクの本人判定や
明示的な実名対応を上書きしない。

Audio の応答にはモデル ID や completed status の保証がない。
要求したモデルと provider が返した値を混同せず、未取得の実モデル ID を作らない。
usage は duration / tokens の区別を保ち、欠落をゼロや無料として補わない。
API エラー本文、Authorization、キー、任意の上流診断は保存・公開しない。

## 保存と再開

区間の指紋には音声 hash、track、sample 範囲、分割版、接続版、モデル、
実効言語・固定パラメータ・アダプタ版を含める。epoch・取得日時・秘密は含めない。
全区間の固定順の一覧から入力全体の指紋を作る。

`preprocess/transcription/` に計画、区間結果、試行台帳を保持する。
試行台帳は区間の指紋を共通キーとし、計画とは分ける。別トラックの追加などで
全体計画が変わっても、同じ区間の成功や結果不明を引き継ぐ。
計画作成から API 呼び出し、完成した track の公開まで会議単位の実行ロックを保持し、
別プロセスが実行中の pending を再起動後の不明状態として再送できないようにする。
送信前に attempt ID・epoch・pending を保存して fsync する。
成功結果は hash を照合して epoch にかかわらず再利用する。
台帳の破損や成功成果の欠損を、黙って再送可能な cache miss にしない。

全区間の結合が完了した track だけ、不変の Transcript を保存して
既存 `transcripts/own-<track>` の参照を更新する。途中結果や履歴を
manifest の transcripts 名前空間へ登録せず、未完成 source の混入を防ぐ。
epoch だけの変更は完成 Transcript と下流の指紋を変えない。

送信後の切断・timeout・不正応答・保存失敗・取消は結果不明として残す。
再起動、DB 再構築、時間経過、force、選択の解除・復元では解除しない。
成功を保存してから取消を判定し、再開時の重複送信を避ける。

## 結果不明の明示的な再試行

`regenerate` に任意の `transcription_retry` を追加する。これは保存設定ではなく、
一つの不明区間を再送する確認であり、次の閉じた値を持つ。

- `input_fingerprint`: 確認した全体入力の SHA256
- `chunk_fingerprint`: 再送を許可する一つの区間の SHA256
- `blocked_epoch`: その区間が記録した直近の不明試行の epoch

API 音声認識でも `expected_config` を必須にする。
現在の選択 epoch が blocked_epoch より大きく、実入力・対象区間・直近 epoch が
確認値とすべて一致するときだけ、一度の再送を許可する。
最初の ASR 送信前に照合し、不一致なら音声を送らず停止する。
再送前の pending 保存と同時に blocked_epoch を新しい値へ進める。
再送が失敗しても同じ確認を再使用せず、新しい確認を必要とする。

現在の計画の未解決区間を事前に調べ、対象以外の unknown は自動再送しない。
複数ある場合は最初の一つを確認対象にし、別の unknown には別の確認を要求する。
成功区間は再利用し、許可した一つの区間と未処理分だけを続行する。
epoch を増やしただけの通常処理・自動処理から、この確認を迂回できない。

`get_job_status` の型付きエラー情報に、stage、reason、結果不明フラグ、
二つの指紋、blocked_epoch、track、区間番号・総数・成功済み数・sample 範囲を返す。
アプリは文字起こしタブの「不明区間を再送…」で対象と重複課金を確認し、
「API への再送を開始」で epoch を更新してから
保存結果が確認した設定と一致することを確かめ、regenerate を呼ぶ。
ジョブが失われても同 epoch の再開は送信せず、台帳から同じ確認情報を返せる。

録画・取り込みの自動処理は、明示保存した API 選択・api_ok と既存の
自動処理操作を利用し、受理した設定の snapshot を実行開始時に照合する。
自動処理には不明区間の再送確認を渡さない。録画の停止・確定は処理失敗より先に行う。
API 音声選択がある `regenerate` と再生成付き `register_context` は、確認済みの全設定を
`expected_config` に要求する。`register_context` は不明区間の再送を許可しない。

## 再送要求の受付が不明な場合

ASR 区間の結果不明と、`regenerate` 要求が受け付けられたか不明な状態を分ける。
後者ではアプリが元の request ID・本文をメモリに保持し、自動再送を止める。
会議の切替や確認画面の取消だけでは、未解決の受付・課金結果の警告を消さない。

ジョブ一覧の「文字起こしタブで元の要求を確認」から、該当会議の復旧操作へ戻る。
「同じ要求を再送して受付を確認…」→「同じ要求を1回再送」は、保持した同一 ID・本文を
利用者が明示的に送る操作である。未受付だった場合は音声処理・課金が始まり得るため、
読み取り専用の状態照会とは説明しない。ジョブの受付と idempotency 応答の保存は原子的ではない。
手動再送で成功応答と job ID を得た場合だけ、元の受付不明を解除する。
手動再送のエラーだけを根拠に元の要求が未受付だったとは判断せず、保留を維持する。
初回の再生成要求がジョブ受付前の確定的な検査で拒否された場合は、受付不明とは区別する。

この復旧情報はアプリのメモリ内だけで、アプリ再起動後の永続復旧は対象外。
サーバー側の区間成功・結果不明の台帳は残り、通常の処理は不明区間を自動再送しない。
読み取り専用の受付確認 API の追加は0.5.0に含めない。

## 検証

0.5.0 の先行範囲は実装・ソース検証済み。以下は全体検証結果で、個別テストの合算ではない。
過去の検証記録やソース検証の成功を、0.5.0の公開成功とは扱わない。

2026-08-29 時点の確認結果は次のとおり。

- Python 全 4,995 件成功、5 件 skip、2 件対象外（706.60 秒）。
- Swift 全 691 件成功（27.43 秒）。
- Python 2 パッケージの wheel、Swift build、Ruff check / format（328 ファイル）、compileall、製品 0.5.0・契約 5.0.0・37 ツールの整合が成功。
- fake HTTP と `MCPClient` / `NarumiClient` の実装を組み合わせ、旧契約 3 / 4 の互換性、ASR の自動再送を行わないこと、元の要求 ID・本文による手動復旧を確認した。

契約テストを先に通し、実 API・実キー・実会議を使わずに実装する。
合成 WAV で分割・時刻・末尾・2トラック・上限を確認し、fake HTTP で multipart、
応答型、secret 反射、取消、結果不明、再起動、成功再利用を検証する。
MCP / CLI / Swift の保存・再読込・モデル選択・送信確認・明示再試行を統合検証する。
実認識精度、区間境界の品質、実 API・実 Keychain・更新後 GUI は未検証。ソース検証とは別に確認する。
