# 複数プロバイダによるテキスト議事録生成

作成: 2026-08-29。製品0.6.0 / 契約6.0.0の実装範囲。
この文書は設計であり、実装・検証・公開の完了報告ではない。

## 利用者の操作

会議設定とプロファイルで、従来の処理・単独モデル指定・複数案の統合を選ぶ。
複数案では生成担当2〜4件と統合担当1件を設定する。
担当ごとに接続、正確なモデルID、対応する推論設定と出力上限を選択する。
同じプロバイダの別モデルを使用でき、統合担当は生成担当のモデルと同じでもよい。
選択の保存だけでは生成や外部送信を行わない。

実行確認では、全担当の接続・モデル・送信先・費用区分を表示する。
API担当を含む場合はapi_okが必要で、許可を自動変更しない。
既存のASR確認と併用し、音声認識と議事録の送信許可を混同しない。
作成中・成功・失敗・取消・結果不明を担当別に表示し、成功した案は完成版がなくても閲覧する。
完成版のエクスポートは、すべての必要な生成・統合・検証に成功した版だけを対象にする。

最初の対応はCodex App Server / OpenAI API / Anthropic API / Ollamaのテキスト生成。
Claude Agent SDK生成、画像送信、全工程のProcessingConfig移行、並列実行は含めない。
実行並列数は1固定。同一プロバイダの別モデルでも既存の排他と一人の保存担当を維持する。

## 設定契約

MeetingConfigにnullableなminutes_ensembleを追加する。
既存minutes_modelとの同時指定を拒否する。両方nullなら既存llm_provider経路を維持する。

    minutes_ensemble = {
      generators: [{id, label, selection: ModelSelection}],
      synthesizer: ModelSelection
    }

生成担当IDは一意で安定し、表示名と分離する。2〜4件を厳密に検査する。
表示名は空白だけを拒否し、最大80文字とする。表示名と配列順をモデルのプロンプトへ渡さない。
省略は保存済み設定の保持、nullは解除、objectは全置換。
モデル選択のprovider、connection_id/revision、model_id、閉じたparameters、cache_epochを再利用する。
会議・プロファイル・録画開始・expected_configのすべてが同じ定義を参照する。
実行と設定保存には既存の全設定CASを使用し、確認後の選択変化を黙って採用しない。

全生成担当・統合担当・ASRの検証は一度のProviderStore transactionで行う。
すべての担当を実行前に検証し、各外部呼出しの直前にも再検証する。
公開直前にも全担当とASRを同時に再検証し、実行の認可pinと内容条件に一致することを確かめる。
最後の検証からmanifestの原子的な公開まで、同じProviderStore transactionを保持する。
接続の削除参照は全担当と統合担当を含み、接続無効化・認証変更・catalog変更を無視しない。
単独生成のparams、fingerprint、既存checkpointの意味は変更しない。

## 原文・生成・統合

一つの実行に対する原文と共通の会議ブリーフを不変artifactとして保存する。
モデル非依存の固定ブリーフ予算を用い、優先度による不採用項目と理由を来歴へ残す。
生成担当を変更しただけで他担当へ渡るブリーフが変わる設計にしない。

原文の根拠単位は内容、正確な時刻、話者、文字範囲から決定的に識別する。
元のmerged segment ID、source参照、文字範囲は当時の原文artifactに保存する。
全体の連番IDや全会議hashを各区間のprompt指紋へ混ぜず、無関係な区間の再利用を保つ。
同一時刻・同内容の重複を捨てたり、曖昧な別発話を一つに対応付けたりしない。

各担当が同版の原文とブリーフを独立に読んで根拠付きの案を作る。
モデルごとの分割は許容するが、原文の固定時間窓を越えて後続区間の分割をずらさない。
長い一発話は文字範囲を残して分割し、末尾切捨てをしない。
生成応答は閉じたJSONとして検証し、主張には渡した原文の根拠IDを要求する。
原文ID・範囲・型の整合検査は、内容の真実性や意味的正しさの保証ではない。

統合は専用プロンプトで全担当の案と原文根拠を照合する。
同じ意見の数だけで事実を決めず、不一致は確認事項として残すよう指示する。
長文では区間ごとの根拠付き統合から開始し、その成果と対応する引用原文を段階的に縮約する。
最後は検証済みの一つのJSONから決定的に完成版Markdownを描画する。
最後の一呼出しに全原文を収めたとは表示しない。各段で処理した入力と参照を記録する。
モデルが重要な情報を保持する保証はしない。構造・参照・入力境界の検証と品質評価を区別する。

不正なJSON、存在しない参照、過大な応答、縮約しない応答は停止する。
自動の再生成・別モデルへの代替・placeholderでの完成扱いを行わない。
応答を受け取ったが検証に失敗した場合も、外部呼出しが無かった扱いにはしない。

## 保存・再利用・再試行

run、node、外部call、attempt、artifactの識別子と、内容のfingerprintを分離する。
会議共通のcall台帳で成功・未完了・不明状態を管理し、新しいrunを作って不明状態を回避しない。
秘密値、認証状態、観測時刻は内容指紋に含めない。
接続revisionは現在の承認照合に使用するが、秘密のrotationだけで成功内容を失効させない。
接続IDによる帰属と、endpoint・実効モデル・parameters・runtimeによる内容条件は別々に保つ。
成功cacheは接続IDごとに分ける。unknown barrierは接続IDも除外し、接続の作り直しによる迂回を防ぐ。
別接続への確認済み再送では、元の不明attemptと現在の接続を表示し、元の応答や課金が確定したとは記録しない。

各callの送信前にpendingと予算消費を永続化し、応答成功は自己完結するreceiptとして先に保存する。
成功保存後、索引・run更新前の停止からは保存済み応答を再利用し、再送しない。
破損した成功成果をcache missと見なして外部へ再送しない。
workerはmanifestを書かず、coordinatorだけが成果登録と完成版の公開を行う。
すべての必要なdraftと統合結果を検証してから一度だけminutes/vNへ登録する。
既存の完成版は保持する。

通常の再開では成功nodeを再利用し、既知の未完了だけを処理する。
Aのモデル変更ではAと依存する統合だけ、統合担当の変更では統合だけを処理する。
表示名・並び順だけの変更では外部呼出しを追加しない。
原文の部分変更は、該当区間とその下流だけを再処理する。

cache_epochは既知成功から新しい生成を明示的に要求する値とする。
unknownはepochの値、設定解除・復元、別run、担当IDの付替えでは解消しない。
不明callの再送はregenerate.minutes_retryで、run/node/call/blocked_attemptを明示確認する。
run/node/callは現在の確認対象を表し、元の送信先・run・nodeはblocked_attemptから復元する。
古いrunの確認から現在の再送先を推測せず、現在の必須nodeと依存が一致しない確認を拒否する。
全expected_configと現在の不明receiptを照合し、確認を新pendingとして送信前に一度だけ消費する。
他の不明callや古いattemptの確認には流用しない。
対象の再送成功後は同じ確認済みrunの未実行依存処理と統合を継続する。
別の不明callは再送せず、別枝の既知失敗もこの確認だけで追加再試行しない。
minutes_retryはASRより前に、現在の上流入力と対象runの入力条件を外部送信なしで照合する。
新しいASR送信が必要な場合や現在入力を決定できない場合は、proofを消費せず通常処理を先に求める。
同じrequest_idの復旧は同一の要求本文に限定し、受付結果不明時には自動再送しない。
送信後の取消はサービス側処理や課金停止を保証しない。
取消したrunは、新しい明示操作で同じ累積回数を維持して再開できる。
取消状態のまま公開せず、過去のinvocation・receipt・取消記録を書き換えない。

## 上限

一runの生成試行は最大64回。再開と確認済み再送も累積する。
再利用した成功応答は新たな呼出し数に数えない。
この数はnarumiが開始する生成試行の上限であり、SDK内部の全HTTP通信回数を保証しない。
新runは別枠であり、会議全履歴の金額上限・厳密なtoken見積り・並列費用予約は保証しない。
縮約は最大6段で、入力文字数が減らない場合は停止する。
入力上限は既存と同じアプリ側の保守的な文字数制限とし、context不明は能力値を補完しない。
未知contextでは12,000文字、既知contextでも最大24,000文字。これはモデルのtoken上限保証ではない。
選択した小さいcontextでプロンプトが成立しない場合は送信前に停止する。

## 公開APIとUI

新しい読み取りツールはlist_processing_runs、get_processing_run、get_processing_artifactの3件。
一覧は既定20件、最大100件のopaque cursor方式とし、作成日時とrun IDで安定した順序を保つ。
この版ではminutes ensembleだけを扱い、既存単独生成に架空のrunや来歴を補わない。
会議IDとscopeに加え、不透明なrun/artifact IDで検索する。任意ファイルパスを入力として受け付けない。
artifact取得は指定runに所属または再利用された成果に限定する。
get_minutesはrequired nullableな型付き来歴を返し、旧版はnull、複数案の版は当時のrun・担当・成果IDへ辿れるようにする。
get_job_statusの成功結果もrequired nullableなrun参照とし、複数案以外はnullにする。型付き不明call情報を返すが、揮発jobをdurable runと混同しない。
製品CLIにも同じ設定・読み取り・確認付き再試行を契約から公開する。

Swiftでは生成担当カード2〜4件と統合担当カードを、安定した担当IDで管理する。
接続・モデル候補の非同期状態はカードまたは接続ごとに分離し、応答を互いに失効させない。
議事録タブは完成版と実行ごとの案を分け、部分成功でも比較できる。
担当・model・実効parameters・実行/再利用・観測usageを表示し、欠損値をゼロや推測値で埋めない。
選択が同一で成果を共有した場合は、独立した二回の生成とは表示しない。

新契約は6.0.0、公開ツール数は40とする。
ensemble_generationは上記縦断実装と検証が揃う場合だけtrueにする。
上限4担当・並列数1・64生成試行・テキストのみを能力通知に含める。
minutes_ensemble_limitsにはmax_generators、max_concurrency、max_generation_attempts_per_run、
max_reduction_depth、input_modalitiesを返す。上限通知を実行許可とみなさない。
旧契約5以下の開発用接続には新設定や再試行fieldを送らない。

## 検証・公開条件

契約変更と契約テストを先に通し、実装とfake統合を追加する。
単独生成・ASR・旧サーバー互換を維持する回帰テストを実行する。
部分再利用、全選択事前検証、対象callだけの確認再送、再起動、DB再構築、取消、保存障害を確認する。
案が一部だけ成功した状態や統合検証の失敗から完成版を公開しない。
根拠JSONのsnapshot、異なるcapacity、長文・非縮約・上限停止、scope・成果参照を検証する。
アプリのカード状態、比較、同意、旧wire、新しいAPIのMCP縦断を検証する。
独立レビュー、Python/Swift全検証、wheel/版/配布内容の整合を確認する。
実プロバイダ・実認証・会議・GUIは通常テストで使用せず、未検証範囲を明記する。
署名・公証・公開配布物の照合はコードの検証とは別に実施する。
