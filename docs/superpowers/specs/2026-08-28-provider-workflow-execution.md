## 1. 実行単位

一回の処理要求を `run`、再利用・再試行できる工程を `node`、
一回の外部要求を `call` として区別する。MCP の要求 ID はこれらの代わりにはならない。
run は会議の入力版、設定、送信許可、接続の実行条件を固定する。
処理中のプロファイル・環境変数・ユーザー設定を読み直して担当を変えない。

| node | 主な入力 | 成果 |
|---|---|---|
| `transcribe:<track>:<chunk>` | 音声 hash・変換条件・実効 ASR モデル | 時刻付き文字起こしと使用量 |
| `visual_speakers:<interval>` | 対象画面・区間・実効 Vision モデル | 発話中の話者についての証拠 |
| `integrate:<interval>` | 区間の各発話・話者証拠・語彙・実効モデル | 根拠付きの統合発話 |
| `draft_chunk:<generator>:<chunk>` | 統合発話・ブリーフ・必要な画像・実効モデル | 原文への参照を持つ要約 |
| `draft:<generator>` | その担当の要約・会議情報 | 一つの議事録案 |
| `synthesis_chunk:<chunk>` | 対象の各案・対応する原文 | 案の比較・根拠・矛盾 |
| `synthesis` | 比較結果・各案・根拠 | 最終候補 |
| `publish_minutes` | 検証済み最終候補・provenance | 追記型の完成版 |

前処理・pHash・決定的アライメントは引き続き固定工程とする。
単独生成は `draft` を検証して完成版にし、別の synthesis 呼出を加えない。
`plain` は既存の文字起こしベースの議事録を生成し、LLM を呼ばない。
複数生成は、選んだ全担当と synthesis の成功を完成条件にする。

長い原文はタイムスタンプと安定した発話 ID を使って決定的に分割する。
プロンプト予算に収まらない入力を黙って切り捨てない。
段階的な要約・統合が必要な場合は、その node と入力を実行計画へ含める。
独立した案の生成には、他の生成担当の案を渡さない。

### 未確定の下流と録画前の確認

ASR の結果や LLM の要約が未生成なら、下流の入力 hash と chunk 数は未確定である。
プレビューはそれらを `conditional` とし、入力の依存関係・分割手順・最大呼出数を示す。
既知入力と確認済みの処理手順を `plan_fingerprint` に固定し、成果が出るたびに
coordinator が決定的に graph を展開する。確定した hash と node は run に追記する。
確認済みのモデル・送信先・データ種別・上限を超える展開は実行せず、確認待ちにする。
段階的な要約の追加を、黙った送信・追加予算として扱わない。

録画前は具体的な実行計画でなく、入力 hash を含まない `RecordingAuthorizationEnvelope` を確認する。
録画開始時にプロファイル・接続・許可・処理手順の版を照合し、会議へ不変に保存する。
停止後は録画を先に確定し、実際の音声長・入力 hash を使って計画を作る。
自動処理は事前許可の範囲内だけで行い、条件が変わった場合は録画を残して確認待ちにする。
録画前の指紋と停止後の入力 hash 付き計画を、同一でなければならない値として比較しない。

## 2. 実効モデルとキャッシュ

実行前に `ResolvedSelection` を作り、実際に送るモデルとパラメータを確定する。
未対応の設定を無視する、別モデルへ自動変更する、API 認証をサブスクと見なす実装は禁止。
ベンダーの応答が実モデル ID を返す場合は、要求値と別に実行記録へ残す。
固定モデルを要求したのに別モデルが応答した場合は、検証失敗として扱う。

生成内容の指紋は canonical JSON と入力ファイルの SHA-256 から作る。

| 含める値 | 含めない値 |
|---|---|
| 対象区間の本文・時刻・話者・根拠 | 実行日時・ジョブ ID |
| 注入したブリーフ・語彙・画像の実内容 | 未使用のコンテキスト・全 manifest の更新日時 |
| プロバイダ・接続 ID・非秘密の送信先識別子 | API キー・token・秘密の hash |
| 実効モデル ID・取得できた版 / digest・cache epoch | 単純な秘密ローテーションの版 |
| 実際に適用した推論設定・出力上限・seed | UI の表示名・生成担当の並び順 |
| プロンプト版・アダプタ版・実行に影響する runtime 版 | 利用量・費用・キャッシュ命中回数 |

同じ入力から同じ版を返すのは、保存した成功成果を再利用することによって保証する。
LLM を再度呼べば同じ文字列が出る、という意味ではない。
alias 実体が不明なら要求 ID と cache epoch を固定し、その限界を provenance に記録する。
新しい実体を試す操作は、設定世代を進めた別の実行として扱う。

| 変更 | 再実行するもの | 再利用するもの |
|---|---|---|
| 担当の表示名・一覧順 | 表示メタデータだけ | すべての生成内容 |
| 生成担当の追加 | 追加担当の要約・案、必要な synthesis | 既存担当の案、発話統合、ASR |
| 一担当のモデル・設定 | その担当の要約・案、必要な synthesis | 他担当の案、発話統合、ASR |
| 統合担当のモデル・設定 | synthesis のみ | 全担当の案と原文 |
| 特定区間の外部発話・話者修正 | 影響区間の統合・要約、依存する案と synthesis | 影響しない区間 |
| ASR モデル | 対象トラックの ASR、差分に依存する工程 | 同じ hash の前処理・無関係なトラック |
| Vision モデル | 画面の話者証拠と影響区間の下流 | キースライド抽出・ASR |
| キーのローテーション | 認証・計画の再確認 | 同じ非秘密の実行条件で作った成功成果 |

完成版を組み立てる最終処理が必要でも、変更していない区間の LLM 処理を再実行しない。
設定変更に既存の全体 `force=true` を流用しない。
再実行を明示した場合も対象 node を計画に表示し、その費用・送信許可を確認する。
同じ指紋の node を明示再実行しても、以前の成果ファイルを上書きしない。
指紋は入力条件の識別子、`artifact_id` は一回の成功成果の不変 ID として分ける。
キャッシュ索引は指紋から採用する成功成果 ID を指し、成功・検証後にだけ参照を更新する。
過去の完成版は当時の成果 ID を参照し続ける。下流の再生成は新旧成果の内容 hash で判断する。

## 3. 正本と並列処理

成果と再開状態は会議バンドルに置く。DB はこれらの索引であり、唯一の保存先にしない。

```text
preprocess/transcription/<fingerprint>/chunks/<chunk-id>/<artifact-id>.json
transcripts/<source-id>/<artifact-id>.json
merged/artifacts/<interval-id>/<artifact-id>.json
context/briefs/<artifact-id>.json
minutes/
  budget/events/<event-id>.json
  budget/ledger.json
  runs/<run-id>/plan.json
  runs/<run-id>/state.json
  runs/<run-id>/calls/<call-id>.json
  work/<generator-id>/<fingerprint>/<artifact-id>/chunk.json
  drafts/<generator-id>/<fingerprint>/<artifact-id>/draft.md
  drafts/<generator-id>/<fingerprint>/<artifact-id>/provenance.json
  syntheses/<fingerprint>/<artifact-id>/result.json
  vN/minutes.md
  vN/meta.json
```

音声認識の分割計画・chunk 結果・途中状態は `preprocess/transcription/` に置き、run から参照する。
`transcripts/` へは全 chunk の検証と結合が済んだ source だけを登録する。
読取側も manifest に確定済みとして登録された source を対象とし、途中 JSON を glob で発話として読まない。
機械的に発行した成果 ID と実パスの対応を manifest で管理する。
確定 Transcript・統合済み発話・ブリーフ・画像・話者証拠も、参照先の版を不変に保存する。
根拠は source 成果 ID とその中の発話・区間 ID を組にし、ASR 再生成後も当時の原文を取得できるようにする。
固定パスを互換性のために残す場合は最新成果の便宜コピーに限定し、過去版の参照先には使わない。
API から任意の相対パスを指定して読めるようにはしない。
すべての成果は会議の scope を継承する。会議をまたぐ生成キャッシュは初期対象外。

現行 `Bundle.save()` は同じ一時ファイル名を使うため、各並列ワーカーから
`Bundle.run_stage()` と manifest 更新を同時実行してはならない。
ワーカーは専用の一時領域で生成し、一つの coordinator が検証・hash・永続化・manifest 登録を行う。
会議単位の排他で coordinator の二重起動も拒否し、予算予約と成果登録の競合を防ぐ。
ワーカーごとに SDK セッション・環境変数・プロセス境界も分離する。
グローバル環境変数を書き換えて担当を切り替えない。

call / chunk が成功するたびに、原子的保存と durability の確認を済ませてから次へ進む。
モデルを切り替えた際も、以前の成功キャッシュを「今回使わない」だけで消さない。
同じ指紋の成功成果を同一 run 内で二重に生成しないよう、coordinator が予約する。
中間成果と完成版の確定は区別し、検証失敗・取消の案を最新の完成版へ昇格させない。

## 4. 取消・クラッシュ・結果不明

call 状態は `prepared / submitted / succeeded / failed / unknown / cancelled` とする。
外部送信直前に `submitted` を永続化し、応答と成果を保存してから `succeeded` にする。
送信とローカル記録を原子的にはできないため、クラッシュ後の `submitted` は安全側に `unknown` とする。

| 状態 | 再開時の扱い |
|---|---|
| 送信前で未実行が証明できる | 許可・上限を再確認して実行可能 |
| 成功結果が永続化済み | 入力・指紋・hash を照合して再利用 |
| ベンダーが明確に拒否した | 理由を表示。認証修正や明示再実行を待つ |
| 送信後の timeout / 通信断 / クラッシュ | 結果・課金不明。無条件に再送しない |

ベンダー側に結果照会・冪等キーの正式な仕組みがある場合だけ、その仕様の範囲で照合する。
`get_processing_run` は保存済み状態の読取、`reconcile_processing_call` は対応する外部結果照会とする。
照会で新しい生成を開始しない。非対応・再照会不能なら理由付きで `unknown` を維持する。
それ以外は call ID と重複課金の可能性を表示し、明示確認した再試行を別 attempt として残す。
narumi の `request_id` は MCP の二重受付を防ぐだけで、外部 API の exactly-once を保証しない。
SDK の内部 retry は抑制・把握できる範囲を検証し、不能な場合は上限や課金を保証しない。

取消は各呼出前、ストリーム受信中、各保存後に検査する。
Codex / Claude は公式の中断経路を使い、所有セッション・所有プロセスだけを終了する。
HTTP 接続の中断が、ベンダー側の処理終了や請求ゼロを意味するとは表示しない。
取消直前に成功した結果は保存できるが、取消済み run の完成版を自動確定しない。
ローカルの子プロセスが残っている場合は稼働状態を維持し、アプリ更新を許可しない。

既存ジョブ状態と run 状態を分ける。確認待ち・結果不明は run 側に記録し、
外部ジョブは適切な構造化エラーで終える。永続 run と call 記録から後日再開できるようにする。
成功済みの担当を除外せず、失敗担当だけ再試行できる。
担当を削除して統合する操作は、新しい構成・計画として確認し直す。

## 5. 音声認識 API

### 初期対応

| モデル | 時刻の取得 | 初期の扱い |
|---|---|---|
| ローカル Whisper | エンジンの発話 / 単語時刻 | 既存経路を維持し実効モデルを明示 |
| OpenAI `whisper-1` | `verbose_json` と対応する timestamp 指定 | 対応 |
| OpenAI `gpt-4o-transcribe-diarize` | `diarized_json` の区間・話者 | 対応。必要な chunking 設定をモデル別に適用 |
| OpenAI の時刻なし文字起こし経路 | 文章のみで時刻がない | 理由付きで選択不可。別の時刻付与設計後に追加 |

モデルによって言語・prompt・応答形式などの引数は異なる。
共通オプションを一律に送らず、アダプタのモデル別 schema で変換・拒否する。
現在のファイル入力上限は 25 MB。上限や応答形式は実装時にも公式仕様を再確認し、
能力表・テスト・上限の版を揃える。
出典: [OpenAI File transcription](https://developers.openai.com/api/docs/guides/speech-to-text)。

### 決定的な分割・再開

1. 元トラックから送信用音声を固定パラメータで作り、hash・sample rate・変換条件を記録する。
2. 上限未満に分割する。固定した無音検出と最大時間・容量を使い、境界・元時刻・hash を保存する。
3. 各ファイルの実バイト数を送信直前に確認する。予想ビットレートだけで容量内と判断しない。
4. chunk 単位で許可・上限予約・送信・保存を行う。成功 chunk は再送しない。
5. 応答の時刻を音声尺と照合し、元トラックの offset を加えて共通時刻へ戻す。
6. overlap を使う場合は、保存済みの対応規則で重複を除去する。重複・欠落を LLM で隠さない。
7. 全 chunk の検証後に一つの transcript source として確定し、差分を次工程へ渡す。

返却時刻の有限性、順序、範囲、text の有無、speaker ラベルの形式を検証する。
元トラック時刻と API 内部の chunk 時刻を二重に offset しない。
話者 ID はトラック・chunk の名前空間で分け、別 chunk の `A` が同じ人物とは扱わない。
名前の確定は既存の証拠に基づく層へ渡し、API の仮ラベルを実名にしない。
`known_speaker_references` の声紋用音声は初期対応に含めず、別の明示同意設計を必要とする。

### 時刻なしモデルを分ける理由

本文へゼロ・均等割りの時刻を付けて `Segment` を満たしてはならない。
入力 chunk の範囲は実測値だが、発話の開始・終了とは意味が異なる。
既存の anchors は発話開始差を使い、intervals は近接区間を連結するため、
chunk 範囲をそのまま入れると時計補正や区間境界を壊し得る。

後続段階では、ローカルの時刻付与工程か、発話時刻と独立した `audio_window` の型を設計する。
後者は専用の対応表と精度情報を検索・議事録・エクスポートまで伝播し、
画面との同期・話者実名・発話順を自動確定しない。小さなタグ追加だけでは対応完了としない。

## 6. 根拠と最終版の検証

各案は、要約・決定事項・担当者・期限・確認事項に元発言 ID と該当区間を持つ。
議事録案同士の一致だけを根拠に事実を増やさない。
異なる案が矛盾した場合は原文を照合し、確定できなければ確認事項として残す。
モデルの根拠参照は未信頼入力として検証し、存在しない ID・別会議の ID を拒否する。

manifest と完成版メタデータへ、生成方式、全担当、実効モデル、プロンプト版、
入力成果 ID、根拠の版、実際に取得できた利用量を記録する。
推論強度は記録するが、SDK が流す内部の思考過程を議事録やログへ保存しない。
SDK 自身が入力・応答・イベントを履歴ファイルへ保存する経路も別に検査する。
対応する固定版で履歴停止が適用されることを確認し、専用ディレクトリやログの除外だけで安全とは扱わない。
停止不能な版は利用不可とし、保持する内容・期間・権限・削除方法の追加設計と承認を先に行う。
確認先: [Claude の保存ディレクトリ](https://code.claude.com/docs/en/claude-directory)、
[CLI reference](https://code.claude.com/docs/en/cli-reference)。CLI の設定が SDK に適用されるかも検証する。
全案と synthesis の検証後にだけ、既存の `minutes/vN` へ新しい版を追加する。
最終統合担当を `provider` として表示する場合も、全生成担当の provenance を省略しない。

## 7. 送信許可と費用の実行時検査

各呼出は、保存した profile / meeting の許可上限と現在の無効化状態を両方検査する。
許可の拡大は新しい計画で確認し、縮小・接続無効化は次の送信を止める。
ASR、Vision、発話統合、各案、synthesis、自動エクスポートを一つの確認表に含める。
Notion の送信や Ollama の接続を、LLM 名の静的分類だけで検査済みと扱わない。

Ollama は数値 loopback に接続先を固定し、proxy・redirect を使わない。
モデルがローカルであることを検査できない場合は `local_only` で利用不可にする。
外部 API はアダプタが許可する公式 endpoint だけへ接続する。
SDK は narumi 専用の設定・環境・作業ディレクトリを使い、別の認証・送信先設定を継承しない。

並列呼出の金額上限は coordinator が事前予約し、取得した実績で精算する。
台帳は会議単位とし、run・明示再試行・モデル変更をまたいで既支出と不明予約を引き継ぐ。
`minutes/budget/events/` の追記記録を正本にし、`ledger.json` は検証・再構築可能な集計とする。
送信前の予約、実績、取消・照会による精算、確認済みの上限変更を記録し、減額や枠解放には根拠を残す。
新しい request ID や attempt を作るだけで予算を補充しない。追加予算は保存と実行確認を必要とする。
入力・出力上限・確認済み単価から保守的な上限額を出せない場合、金額保証モードでは実行不可。
金額不明を認める場合も、明示した呼出数・音声長・出力上限を検査する。
呼出数が narumi の要求数なのか SDK 内部 retry も含むのかを UI と記録で区別する。
結果不明の呼出は課金予約を維持し、枠を空けて無制限に再試行しない。
入力の音声長制限は会議の尺、課金見積りは送信した各トラック・chunk の累計として区別する。
音声の overlap・再送も課金側へ加算する。再試行のプレビューは残枠と追加の最大消費を表示する。

## 8. データ移行と回復

manifest の旧版と新版を読める reader を先に用意する。
新しい処理設定・成果参照を保存するときは manifest の版を上げ、原子的に移行する。
起動しただけで全会議を書き換えない。移行前の manifest と移行記録を保存する。
新データを旧アプリが読めないことを明示し、無断でダウングレードしない。

旧版のモデル・prompt・実装版が不足する成果は、閲覧用の過去版として保持する。
新しい実行指紋に合うと証明できない成果を、そのまま新キャッシュへ登録しない。
旧データの曖昧さを補う初回の再処理が必要なら、対象範囲・送信・費用を確認画面に出す。
新しい方式で記録した成果は、以後の変更で影響部分だけ再処理できるようにする。

DB を削除した状態からも、manifest・run・call・予算イベント・成果ファイルで索引と再開候補を再構築できること。
クラッシュ時の未登録ファイルは hash と所有 run を照合し、検証できるものだけ回復する。
不明な外部処理を「未実行」として自動やり直ししない。
